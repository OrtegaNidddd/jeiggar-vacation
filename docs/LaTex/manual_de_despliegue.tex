\section*{Introducción}
\addcontentsline{toc}{section}{Introducción}
% ==================================================================

El presente manual de despliegue describe el proceso técnico necesario para publicar la plataforma \textbf{Jeiggar Vacation} en un entorno de producción. El documento está dirigido a desarrolladores, administradores técnicos y responsables del mantenimiento del sistema que necesiten instalar, configure, actualizar o verificar la aplicación en un servidor.

Jeiggar Vacation es una aplicación web de una sola página desarrollada con React, Vite y TypeScript. Su capa de datos, autenticación y almacenamiento se gestiona mediante Supabase, mientras que el despliegue de producción se realiza mediante Docker y Nginx. Esta organización permite separar la interfaz web de los servicios del servidor y facilita la administración del sistema en un servidor VPS.

El manual se organiza por fases para que el proceso sea claro, secuencial y verificable. Cada fase incluye los comandos necesarios, la explicación de su propósito y las recomendaciones básicas para evitar errores durante la instalación.

\begin{longtable}{|p{0.40\textwidth}|p{0.50\textwidth}|}
\caption{Componentes principales del despliegue}\\
\hline
\textbf{Componente} & \textbf{Tecnología / Servicio} \\
\hline
Interfaz cliente & React, Vite y TypeScript. \\
\hline
Servidor web & Nginx Alpine dentro de Docker. \\
\hline
Proxy inverso & Nginx Proxy Manager. \\
\hline
Servidor y base de datos & Supabase, PostgreSQL, Auth y Storage. \\
\hline
Contenedorización & Docker con compilación multi-etapa. \\
\hline
Servidor de producción & VPS con Ubuntu 22.04 LTS. \\
\hline
Dominio & Dominio configurado mediante registros DNS. \\
\hline
\end{longtable}

\section{Visión General de la Arquitectura de Despliegue}
% ==================================================================

Esta sección presenta la arquitectura general del despliegue. Su propósito es explicar cómo viaja una solicitud desde el navegador del usuario hasta los servicios utilizados por la aplicación.

El flujo inicia cuando el usuario accede al dominio del sistema desde el navegador. La solicitud llega al proxy inverso, el cual redirige el tráfico hacia el contenedor Docker donde se encuentra Nginx sirviendo la aplicación web. Desde la aplicación, las operaciones de datos se comunican con Supabase para consultar información, validar autenticación y cargar recursos almacenados.

\section{Fase 1: Preparación del Servidor}
% ==================================================================

Esta fase prepara el VPS para recibir el proyecto. Incluye la conexión remota, actualización del sistema, instalación de herramientas base y creación del directorio de trabajo.

\subsection{Paso 1: Conectarse al VPS mediante SSH}

Desde la terminal local, ejecutar el siguiente comando:

\begin{lstlisting}[language=bash]
ssh root@<IP_DEL_SERVIDOR>
\end{lstlisting}

Se debe reemplazar \code{<IP_DEL_SERVIDOR>} por la dirección IPv4 pública del VPS.

\subsection{Paso 2: Actualizar el sistema}

Antes de instalar herramientas, se recomienda actualizar los paquetes del sistema.

\begin{lstlisting}[language=bash]
apt update && apt upgrade -y
\end{lstlisting}

Este comando actualiza el índice de paquetes y aplica las actualizaciones disponibles.

\subsection{Paso 3: Instalar herramientas base}

\begin{lstlisting}[language=bash]
apt install -y curl apt-transport-https ca-certificates software-properties-common certbot git
\end{lstlisting}

\begin{longtable}{|p{0.30\textwidth}|p{0.60\textwidth}|}
\caption{Herramientas base instaladas en el servidor}\\
\hline
\textbf{Paquete} & \textbf{Motivo} \\
\hline
\code{curl} & Permite descargar recursos y probar conexiones HTTP. \\
\hline
\code{apt-transport-https} & Permite obtener paquetes mediante HTTPS. \\
\hline
\code{ca-certificates} & Valida certificados TLS durante descargas. \\
\hline
\code{software-properties-common} & Facilita la administración de repositorios. \\
\hline
\code{certbot} & Permite generar certificados SSL/TLS. \\
\hline
\code{git} & Permite clonar y actualizar el repositorio del proyecto. \\
\hline
\end{longtable}

\subsection{Paso 4: Instalar Docker y Docker Compose}

\begin{lstlisting}[language=bash]
apt install -y docker.io docker-compose-v2
\end{lstlisting}

Para verificar la instalación, ejecutar:

\begin{lstlisting}[language=bash]
docker --version
docker compose version
\end{lstlisting}

El resultado debe mostrar la versión instalada de Docker y Docker Compose.

\subsection{Paso 5: Crear directorio de proyectos}

Se recomienda mantener los proyectos web en un directorio organizado.

\begin{lstlisting}[language=bash]
mkdir -p /var/www/proyectos
cd /var/www/proyectos
\end{lstlisting}

\section{Fase 2: Obtención del Código Fuente}
% ==================================================================

Esta fase permite descargar el código fuente del proyecto desde el repositorio y preparar las variables de entorno necesarias para la compilación.

\subsection{Paso 6: Clonar el repositorio}

\begin{lstlisting}[language=bash]
git clone https://github.com/OrtegaNidddd/jeiggar-vacation
cd jeiggar-vacation
\end{lstlisting}

Después de clonar el repositorio, se deben verificar los archivos principales del despliegue.

\begin{longtable}{|p{0.38\textwidth}|p{0.52\textwidth}|}
\caption{Archivos principales para el despliegue}\\
\hline
\textbf{Archivo} & \textbf{Propósito en el despliegue} \\
\hline
\code{Dockerfile} & Define el proceso de compilación y ejecución del contenedor. \\
\hline
\code{nginx.conf} & Configura Nginx para servir la aplicación web. \\
\hline
\code{.env.example} & Plantilla de variables de entorno requeridas. \\
\hline
\code{package.json} & Define dependencias y scripts del proyecto. \\
\hline
\end{longtable}

\subsection{Paso 7: Configurar variables de entorno}

Vite integra las variables de entorno dentro del paquete final durante la compilación. Por esta razón, el archivo \code{.env.local} debe existir antes de construir la imagen Docker.

\subsubsection*{Copiar la plantilla}

\begin{lstlisting}[language=bash]
cp .env.example .env.local
\end{lstlisting}

\subsubsection*{Editar el archivo}

\begin{lstlisting}[language=bash]
nano .env.local
\end{lstlisting}

El archivo debe contener los valores del proyecto Supabase.

\begin{lstlisting}[language={}]
VITE_SUPABASE_URL="https://xxxxxxxxxxxxxxxx.supabase.co"
VITE_SUPABASE_ANON_KEY="sb_publishable_xxxxxxxxxxxxxxxx"
\end{lstlisting}

Para guardar en Nano se utiliza \textbf{Ctrl + O}, luego \textbf{Enter}. Para salir se utiliza \textbf{Ctrl + X}.

\textbf{Seguridad:} El archivo \code{.env.local} no debe subirse al repositorio. Las variables con prefijo \code{VITE_} son públicas dentro de la interfaz cliente, por lo tanto, la seguridad de los datos debe controlarse mediante políticas de seguridad a nivel de fila (Row Level Security) configuradas en Supabase.

% ==================================================================
\section{Fase 3: Compilación de la Imagen Docker}
% ==================================================================

Esta fase construye la imagen Docker de la aplicación. El proceso utiliza una compilación multi-etapa para generar primero los archivos estáticos con Node.js y luego servirlos mediante Nginx.

\subsection{Descripción del Dockerfile}

El \code{Dockerfile} utiliza una primera etapa para instalar dependencias y compilar el proyecto. La segunda etapa copia el resultado compilado a una imagen ligera de Nginx.

\begin{lstlisting}[language={}]
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci

COPY . .
RUN npm run build

FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
\end{lstlisting}

\diagramfigurehere
{diagramas/docker-build-flow.png}
{Flujo de compilación multi-etapa de Docker}
{Representación de cómo Docker compila primero la aplicación con Node.js y luego transfiere los archivos generados a una imagen final basada en Nginx.}
{fig:docker-build-flow}

\subsection{Paso 8: Compilar la imagen}

Desde el directorio raíz del proyecto, ejecutar:

\begin{lstlisting}[language=bash]
docker build --no-cache -t jeiggar-vacation .
\end{lstlisting}

El parámetro \code{--no-cache} obliga a Docker a reconstruir la imagen desde cero. Esto es útil cuando se han modificado variables de entorno o dependencias.

\section{Fase 4: Ejecución del Contenedor}

\section{Fase 5: Configuración de Dominio y Certificado SSL}
% ==================================================================

Esta fase explica cómo asociar un dominio al servidor y habilitar una conexión segura mediante certificado SSL/TLS.

\subsection{Paso 11: Apuntar el dominio a la IP del VPS}

Desde el panel del proveedor del dominio se deben crear los registros DNS correspondientes.

\begin{longtable}{|p{0.14\textwidth}|p{0.20\textwidth}|p{0.28\textwidth}|p{0.28\textwidth}|}
\caption{Registros DNS requeridos}\\
\hline
\textbf{Tipo} & \textbf{Nombre / Host} & \textbf{Valor / Apunta a} & \textbf{TTL} \\
\hline
A & \code{@} & IP pública del VPS. & Automático. \\
\hline
CNAME & \code{www} & Dominio principal. & Automático. \\
\hline
\end{longtable}

\subsection{Paso 12: Obtener certificado SSL con Certbot}

Si el puerto 80 está administrado por un proxy inverso, puede utilizarse validación DNS manual.

\begin{lstlisting}[language=bash]
certbot certonly --manual --preferred-challenges dns -d tu-dominio.com -d www.tu-dominio.com --email tu-correo@gmail.com --agree-tos --no-eff-email
\end{lstlisting}

Certbot solicitará crear registros TXT en el panel DNS del dominio. Después de agregarlos, se debe esperar la propagación y continuar el proceso en la consola.

\subsection{Paso 13: Configurar Nginx Proxy Manager}

Una vez emitidos los certificados, se copian al volumen del proxy inverso.

\begin{lstlisting}[language=bash]
mkdir -p /var/lib/docker/volumes/parking_nginxmanager_data/_data/nginx/certs

cp /etc/letsencrypt/live/tu-dominio.com/fullchain.pem /var/lib/docker/volumes/parking_nginxmanager_data/_data/nginx/certs/tu-dominio-fullchain.pem

cp /etc/letsencrypt/live/tu-dominio.com/privkey.pem /var/lib/docker/volumes/parking_nginxmanager_data/_data/nginx/certs/tu-dominio-privkey.pem
\end{lstlisting}

Luego se edita el archivo de configuración del host proxy.

\begin{lstlisting}[language=bash]
nano /var/lib/docker/volumes/parking_nginxmanager_data/_data/nginx/proxy_host/1.conf
\end{lstlisting}

Configuración sugerida:

\begin{lstlisting}[language={}]
server {
listen 80;
listen [::]:80;
server_name tu-dominio.com www.tu-dominio.com;
return 301 https://$host$request_uri;
}

server {
listen 443 ssl;
listen [::]:443;
server_name tu-dominio.com www.tu-dominio.com;

ssl_certificate /data/nginx/certs/tu-dominio-fullchain.pem;
ssl_certificate_key /data/nginx/certs/tu-dominio-privkey.pem;

location / {
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
proxy_pass http://159.65.222.34:8082;
}
}
\end{lstlisting}

\subsection{Paso 14: Reiniciar el proxy}

\begin{lstlisting}[language=bash]
docker restart nginxmanager
\end{lstlisting}

\section{Relación con la Base de Datos}
% ==================================================================

Esta sección explica la relación entre el despliegue de la aplicación y la configuración de Supabase. El despliegue de la aplicación no ejecuta migraciones automáticas de base de datos, por lo tanto, la estructura debe estar previamente configurada desde el panel de Supabase.

Para que el sistema funcione correctamente, Supabase debe contar con los siguientes elementos:

\begin{itemize}
\item Entidades \code{countries}, \code{cities}, \code{destinations} y \code{profiles}.
\item Políticas de seguridad a nivel de fila (Row Level Security) activas en cada entidad.
\item Funciones \code{set_updated_at()} y \code{get_country_map_data()}.
\item Triggers de actualización automática.
\item Bucket de almacenamiento \code{destinations}.
\item Permisos de lectura pública para imágenes requeridas por la aplicación.
\end{itemize}

\textbf{Verificación rápida:} Desde un navegador o herramienta de pruebas HTTP, se puede consultar la API REST de Supabase para validar que existan países activos y que las políticas permitan lectura pública.
